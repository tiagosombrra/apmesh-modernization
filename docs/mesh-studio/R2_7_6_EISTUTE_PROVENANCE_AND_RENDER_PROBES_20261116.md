## 3. Main-thread build and memory-scope preflight

Standalone test:
`tools/mesh_studio/web/tests/viewport-r276-sync-cap.spec.ts`.

A separately labeled **synthetic**, deterministic 32×32 two-TRI cell
grid exercises exactly the synchronous cap of 2,048 TRI faces and 1,089
unique vertices. Four independently created index instances measure
copying/build wall time at the cap with original buffers preserved,
plus optional Chromium JS heap estimates and optional Long Task API
samples. Long Task observations have a threshold near 50 ms and **cannot
prove absence of shorter main-thread blocking**. Typed-array copies are
not the full index heap, browser RSS, Worker RSS or GPU VRAM.

**This synthetic case is only a resource-envelope probe; it must never
be presented as a 2k real Bezier/nonmanifold generator result, error
metric, or scientific speedup.**

## 4. Event-to-render opportunity proxy

Standalone test:
`tools/mesh_studio/web/tests/viewport-r276-raf.spec.ts`.

For one P1 original source TRI face, with curved QUADs hidden,
three independently configured pages use the same pixel and default
camera while comparing bounded synchronous BVH, opt-in Worker, and
native VTK. Two excluded warm-up selections per method precede eight
rotated measured rounds. The browser timestamps the capture phase of
the **actual Playwright pointer click**, then observes completion of
the viewer's picker callback and two sequential
`requestAnimationFrame` callbacks after the inspector update.
The exact original face ID and inspector text must match on every
sample; failure is reported, not silently omitted.

The two-RAF interval is **not** a GPU presentation timestamp or
proof of visible pixels; it includes a frame-scheduling opportunity.
Playwright pointer capture is not a physical human input event.
Importantly, this mechanism avoids mixing separate Playwright
`evaluate`/poll waits into the browser-side measurement.

The first execution of this new test passed within
https://github.com/tiagosombrra/apmesh-modernization/actions/runs/43929359757,
but that **overall CI failed** on a separate strict historical manifest
hash assumption uncovered during the same round. Its results should
not be represented as a fully accepted R2.7.6 run. The provenance
check was corrected to **report** rather than conceal the discrepancy.

## 5. Explicit remaining gates

- Verify reproducibility of the larger reference's original per-face
  generator identity and patch/shared-curve ownership; never assume
  OBJ-order face numbers are canonical source IDs.
- Establish accepted/rejected stage-4 semantics independently from the
  archived JSON values and saved candidate mesh.
- Measure full hardware input-to-actually-presented-frame latency
  with physical desktop browser/OS tracing. Two `requestAnimationFrame`
  callbacks are an explicitly narrower proxy.
- Repeat paired/rotated picker latency on actual Linux and Windows
  desktops with documented OS/CPU/GPU/browser; investigate
  headless-only pointer event scheduling from R2.7.4.
- Measure total process/Worker heap, process RSS, native renderer/GPU
  VRAM and long-task behavior under real multi-model workloads.
  Current JS estimates or typed buffer bytes do not satisfy this.
- Obtain independent error-bound and geometric equivalence evidence
  before changing nonplanar visible QUAD handling or enabling R2.8 LOD.

## 6. Decision

**R2.7.6 is a bounded diagnostic exercise, not permission to change
the default selector, increase the main-thread limit or publish
scientific/GPU speedups.** Preserve VTK native as default and both
experiments as opt-in: `?xyzPicker=sync` and `?xyzPicker=bvh`.
No new generator C/C++ changes, geometric LOD or source-patch welding.
Keep PR #239 draft and unmerged; do not tag or release.

The Git source reference and raw JSON CI receipts are useful for
future qualification, but their exact provenance classifications must
travel with all reported timings.

### 7.2 Real P1 pointer-to-two-RAF opportunity proxy

Original controlled P1 source SHA:
`cbf6cd6308ba54544d06c5d562c491eb7d43ddb216365e0e9d188fd3430295e0`.
One source face **#68**, same pixel, QUAD visibility off, two excluded
warmups per method, eight measured pointer clicks per method, rotated
method order. The clicked face ID and post-RAF inspector were matched in
every measured sample.

| Selector | Browser event to picker callback p50 / p95 | Event to second RAF p50 / p95 |
| --- | ---: | ---: |
| Synchronous bounded BVH | 0.2 / 0.3 ms | **29.9 / 31.7 ms** |
| Native VTK | 0.8 / 0.9 ms | **29.9 / 30.6 ms** |
| Worker BVH | 20.6 / 21.0 ms | **46.9 / 47.4 ms** |

The synchronous BVH has lower picker-callback latency than VTK here,
but **not a measurable improvement in the two-RAF render-opportunity
median**. The Worker retains a longer event-to-RAF median. These are
same-host browser scheduling observations, **not OS input-to-pixel or
hardware GPU-present measurements**. The two-RAF metric has an inherent
frame-scheduling baseline and should not be interpreted as GPU time.

### 7.3 Synthetic main-thread cap envelope

Exactly 2,048 flat-grid TRI faces / 1,089 vertices, typed input **64,272
bytes**. Four independent synchronous index constructions registered
**9.6, 5.8, 5.9 and 5.2 ms**. Chrome reported Long Task API support
and **zero tasks above that API's threshold**, but shorter UI blocks
are not excluded. Optional Chromium main-thread JS heap estimates
were approximately **24,500,000 bytes** before/after; this is *not*
an allocation profile of the BVH, a leak test, process RSS, Worker
memory or GPU VRAM. The case is labeled **SYNTHETIC** throughout.

### 7.5 Physical desktop follow-up procedure (not executed by CI)

For a legitimate GPU and OS responsiveness claim, run on known physical
Windows and Linux machines with recorded CPU model/core count, OS,
display scale, display refresh, GPU vendor/model/driver, browser and
Chromium/WebGL renderer information. Use the same immutable SHA/face
IDs/camera/pixels, with a cold build followed by warm repeated randomized
AB/BA (or A/B/C) rounds across multiple independent sessions. Collect
both DevTools task/Worker traces **and** external process-level RSS/peak
working-set measurements; if GPU VRAM cannot be obtained through a
trustworthy platform mechanism, report it as *unmeasured*.
Record any event-to-visible-frame evidence with its timing API
and synchronization limits. Do not reclassify two RAF callbacks as
GPU-presented frames, or treat the legacy Eistute file as an accepted
adaptive epoch without original generator acceptance evidence.
