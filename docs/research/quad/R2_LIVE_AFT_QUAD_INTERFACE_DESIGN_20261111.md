# R2 design — connect real interior QUAD templates to the existing TRI Advancing Front

**Date:** 2026-11-11 UTC  
**Status:** Source-grounded integration design; **not implemented or validated as a live hybrid APMesh path**.  
**Precondition:** [R1 research PR #211](https://github.com/tiagosombrra/apmesh-modernization/pull/211), **not yet merged or certified** at design time. The recorded R1 candidate is `e2e106238d7482656a098f8e26bb3f31ae2a7b4d` with a later source-face-provenance enhancement on the feature branch.  
**Canonical scope:** [corrected roadmap](IMPLEMENTATION_ROADMAP.md), [implementation audit](OPTIN_QUAD_IMPLEMENTATION_AUDIT_20261111.md).

## 1. The user-visible contract

With no `MESH_ELEMENT_KIND` selection, the unmodified `tri`
generator runs. An explicit experimental QUAD selection must **replace**
the interior TRI templates generated by the same refined Quadtree,
then let the established TRI AFT fill the **remaining exterior** of
each patch. Keep curve discretization and per-patch oriented source
boundary intact. A hybrid patch result contains **actual 4-node QUAD**
elements in the interior and **actual 3-node TRI** elements outside,
sharing one continuous UV mesh, rather than two coincident independently
exported surfaces.

Do not activate `quad_uv` in the application until an end-to-end live
hybrid succeeds on a source patch with complete topology/physical checks.
`USE_TEMPLATE` remains independent from the QUAD/TRI type selection;
for an incompatible `quad_uv` + templates OFF combination, fail clearly
rather than silently producing only TRI.

## 2. Source-confirmed live integration boundary

The existing application path is:

`RunApplication` → `GeneratorAdaptive::GeneratorInitialMesh` (coarse
TRI baseline) → `GeneratorAdaptive::AdaptCurve` → `Adapter::AdaptDomain`
(ordered curve-based UV contour) → `AdvancingFront::execute` →
`Quadtree::generate` → `refineAccordingToNeighbors` →
`Quadtree::makeTemplateBasedMesh` (legacy TRI) → `makeInitialFront` →
`makeGeometryBasedMesh` / `makeTopologyBasedMesh` →
`fillMesh` → `improveMesh` → `Adapter` physical XYZ conversion.

Read and preserve:

- `src/crab_mesh/aft/quadtree.cpp::makeTemplateBasedMesh`: it currently
  bundles **root neighbor sort**, `makeOuterVertices`,
  `makeOuterEdges`, and **actual TRI** `root->makeTemplateBasedMesh`.
  QUAD integration must *not* invoke that entire method just to obtain
  boundary edges, or it will already have published overlapping TRI
  templates. Carefully extract/prep only the topology required for the
  QUAD branch, or create an explicit *owned* new QUAD-interface frontier
  that preserves the needed cell observers.
- `src/crab_mesh/aft/quadtree_cell.cpp::makeOuterEdges` builds `Edge`
  objects, associates a Quadtree cell observer, and calls `tree->addFront`
  for edges incident to boundary leaves. Its **original edge
  segmentation is NOT guaranteed** to match all midpoints introduced
  by the new QUAD subdivision. Blindly reusing that source edge list
  is not sufficient.
- `src/crab_mesh/aft/advancing_front.cpp::makeInitialFront` collects
  both patch-boundary `Boundary::getEdges()` and
  `quadtree->GetFrontEdges()` into the initial TRI advancing front.
  The implementation checks `Edge::getCell()` when generating
  geometric candidate vertices via `makeIdealVertex`. New interface
  edges need valid, live cell/metric references, not default/null
  foreign observers.
- The production `Face` type has **exactly three** vertex slots.
  `AdvancingFront::fillMesh` transfers original 3-node TRI
  `Face` owners. `Adapter::AdaptDomain` currently converts each
  resulting `Face` to `TriangleAdaptive` and treats old submesh
  history as `TriangleAdaptive` by static cast. **Do not retrofit
  QUAD into 3-slot Face and do not cast QUAD to TriangleAdaptive.**
  Use a typed QUAD result whose ownership remains distinct until
  complete physical `SubMesh` publication.

## 3. Proposed R2 ownership and boundary contract

For one `(patch, adaptation_step, retry_attempt)`:

1. Read the source model's **existing** curve sample sequence and build
   the same ordered UV patch boundary as the TRI path. Preserve IDs,
   reverse incidence, and any explicit shared-curve-sync setting.
2. Generate/refine exactly the same Quadtree as TRI, with no changes
   to refinement acceptance/neighbor balance. Before any template
   mutation, choose **one** interior mode.
3. On research QUAD, adopt the R1 `UvMesh` plus a one-to-one ordered
   origin record `(cell_id, leaf_ordinal, depth, T1..T6,
   polygon_ordinal)` for every 4-node QUAD. The result must be an
   **owned** transaction: no published partial elements on failure,
   and any rejected selection can leave accepted TRI state intact.
4. Build a canonical UV vertex-ID dictionary for **one patch** (not
   coordinate welding between different geometric sheets). Retain
   QUAD boundary as the exact one-owner QUAD edges: **QUAD-oriented
   CCW edges have the interior on their LEFT**. The exterior TRI AFT
   sees those edges with **reversed orientation** so it fills the
   outside, not the already QUAD-covered interior. Invert only when
   transferring the directed interface, not in the QUAD topology
   witness itself.
5. Reconcile **all QUAD-side midpoint splits** with this reversed
   AFT front. Every individual front segment has one QUAD owner
   and must acquire exactly one exterior TRI owner upon closure.
   Never replace two half-edges by one whole source Quadtree edge.
   The physical 3D vertex ID, patch UV parameter and owner lifetime
   must be shared by both sides of each interface.
6. Provide a typed `InteriorQuadResult` separate from AFT's
   3-node `FaceList`. Seed existing `AdvancingFront` from the
   ordered patch boundary and reversed interior QUAD interface, with
   owned live `Vertex/Edge` structures and valid `getCell()`
   references. The AFT should still generate **only triangles**.
   Avoid calling legacy TRI template publication on the QUAD path.
7. After accepted AFT completion, publish one `SubMesh` with owned
   `NodeAdaptive` values and typed four-node
   `research::QuadrilateralAdaptive` plus existing
   `TriangleAdaptive`, each with its real UV and `PatchBezier`
   XYZ mapping. Verify node/element observer cleanup on rejected
   attempts and destruction.
8. Keep the current TRI path byte-/science-identical; only then
   extend historical mesh error, quality, adaptation and export code
   through typed element dispatch for repeated QUAD runs.

No global node-welding or high-valence sheet pairing occurs in the
initial per-patch R2 solution. Do not infer global manifold validation
from a UV-patch disk proof.

## 4. Mandatory physical/topological invariants

For every successful complete-patch hybrid witness:

| Invariant | Required observation |
| --- | --- |
| Interior substitution | `interior_source_TRI_faces=0` when QUAD selected, and each emitted QUAD has one valid original source leaf provenance |
| AFT completion | AFT TRI faces cover only the complement of QUAD interior; no collisions or duplicate 2D faces |
| Exact coverage | Total signed UV face area equals real patch-domain UV area within stated tolerance, no gaps or overlaps |
| Seam ownership | Every QUAD–TRI interface edge has **one QUAD + one TRI** incident face with opposite winding; **zero dangling seam edges** |
| Shared IDs | One canonical node identity per UV seam site within a patch; midpoint segments cannot be collapsed across a T-junction |
| Real boundary | Original source curve-parameter sequence and physical curve samples unchanged in the selected TRI/QUAD comparison |
| Physical mapping | Quad corner XYZ from the **actual** parameterization and differential reference; no inverted/near-zero Jacobian admitted under specified tests |
| Lifetime | No QUAD borrows a retired `NodeAdaptive`, `Vertex`, `Edge` or `QuadtreeCell` |
| Default parity | Frozen Eistute/Book TRI traces and outputs unchanged in default mode |
| Rollback | Failed AFT or bad QUAD rule leaves prior accepted mesh and original curves unchanged |
| Repetition | Separate later R3 gate: two accepted adaptive iterations with mixed-element history and metrics |

**Boundary negative tests:** reject disconnected or empty interior
unless explicitly admitted and validated per connected component;
impossible winding, duplicate interior TRI publication, unmatched
half-edge, mid-curve physical/UV mismatch, invalid cell observer,
bad convexity, callback exception, partial ownership transfer,
disagreement after curve refinement, and stale previous adaptation
attempt state. Keep negative controls that distinguish rejected
candidates from qualified results.

## 5. Minimal acceptance order

- **R1 (under PR #211):** same actual C++ Quadtree; two exclusive
  template choices; 16 and 42 QUAD small-tree outcomes with 16/20
  directed interface segments, all 12 test cases, *plus ordered
  cell/template provenance per QUAD face*. No real application or AFT
  publication claim.
- **R2a:** build and test a *read-only geometric comparator*
  between the legacy front edge set and the new QUAD interface. Count
  identical, split and unmatched segments and pin the exact midpoint
  acceptance contract; no production mutation.
- **R2b:** add owned active interface seeding in an isolated research
  `AdvancingFront` test. Prove no legacy TRI interior and 100% seam
  edge matching for unit square and one curved patch boundary.
- **R2c:** typed `SubMesh` QUAD + exterior TRI/XYZ and real
  source-PatchBezier CLI candidate, then positive `quad_uv`
  user-visible opt-in; default TRI strictly unchanged.
- **R3/R4:** repeated adaptation and tracked real 3D models;
  curve-sharing/high-valence information is diagnostic, not a
  prerequisite for individual patch interior emission.

**Stop conditions:** do not integrate R1 or start R2 production
modifications with unqualified R1 native GCC/MSVC and required root
scientific gates. A GitHub workflow in the queue is not a pass,
and a cancelled workflow is not a pass. The experimental interior
point rule is NOT an approved reproduction of Bento et al. (1993).
